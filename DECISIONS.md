# Engineering Decisions Log (interview prep)

Format per entry: Problem / Choice / Alternative / Tradeoff / Likely interview question.
Claude Code: append an entry after every phase. Seed entries below.

## 1. No LangChain/LlamaIndex
- Problem: demonstrate understanding, not framework wiring.
- Choice: direct qdrant-client, rank_bm25, sentence-transformers, psycopg.
- Alternative: LlamaIndex would give ingestion + retrievers for free.
- Tradeoff: more code we own; but every interview answer is "here's the 15 lines that do it" instead of "the framework handles it."
- Interview q: "Why not LangChain?" → abstractions hid the retrieval knobs we needed to tune (fusion constant, filter pushdown, rerank cutoff), and debugging retrieval quality requires seeing raw candidates.

## 2. RRF for hybrid fusion
- See docstring in src/retrieval/hybrid.py. Rank-based → no score normalization across incomparable scales. k=60 standard.
- Interview q: "When does hybrid beat dense?" → exact tickers, product names (Blackwell), acronyms (CET1), accounting terms. Show eval rows kw-01/kw-02.

## 3. Structured financials in Postgres, not vectors
- Problem: "revenue over last 4 quarters" needs exactness and arithmetic; embeddings retrieve approximately.
- Choice: XBRL companyfacts → typed rows; canned parameterized queries; router sends numeric questions to SQL.
- Alternative: text-to-SQL. Deferred: injection surface + hard to eval; v1 uses a fixed query catalog.
- Interview q: "How do you combine both?" → MIXED route runs SQL first, injects the result table into RAG context as a numbered source, so the narrative answer can cite the numbers.

## 4. ANN (HNSW) in Qdrant
- Problem: exact kNN is O(N·d) per query; fine at 10k chunks, dead at 10M.
- Choice: HNSW defaults; measure recall vs exact search on our corpus (it'll be ~1.0 at this scale — say that honestly).
- Tradeoff: memory for graph links + approximate recall vs sub-ms search. Knobs: ef (recall/latency), m (memory/recall).
- Interview q: "Why ANN if your corpus is small?" → it isn't needed at this scale; it's the production-path default so scaling is a config change, not a rearchitecture. Knowing WHY it's overkill now is the point.

## 5. Section-aware chunking
- Problem: fixed-window chunking splits Risk Factors mid-sentence into MD&A context; retrieval returns plausible-but-wrong sections.
- Choice: parse Item headers first, chunk within sections, never cross boundaries; section stored as filterable metadata.
- Interview q: "How do you pick chunk size?" → eval-driven: we compare recall@5 at 400/750/1000 tokens if time permits; 750 chosen as default because filings paragraphs are long and bge-small context is 512 wordpieces (chunks are embedded truncated — acknowledge this and note the alternative: smaller chunks or a longer-context embedder).

## 6. Hard filters before similarity for news
- Problem: "NVDA news last week" via pure vector search returns semantically-similar but stale articles.
- Choice: SQL WHERE ticker AND published_at >= now()-7d first; similarity only ranks within the filtered set.
- Interview q: "What's the general principle?" → push deterministic constraints down to the store; use embeddings only for what's genuinely fuzzy.

## 7. Dedup + event clustering for news
- Problem: 20 syndicated copies of one story = fake importance signal and redundant LLM context.
- Choice: URL exact-dedup, headline-embedding near-dedup (>0.90), agglomerative clustering (~0.75) → events; rank events by article count × source diversity.
- Interview q: "Why cluster before summarizing?" → token budget goes to distinct events; count-based importance only works after dedup.

## 8. Storage abstraction: local (SQLite + embedded Qdrant) vs docker (Postgres + Qdrant server)
- Problem: Docker Desktop on Windows drags in WSL2 + virtualization + reboots. Blocking a weekend build on container infra is a bad trade.
- Choice: one seam (`src/common/db.py::get_conn/get_qdrant`), mode flag in config.yaml. SQLite and embedded Qdrant for dev; Postgres and Qdrant server for deployment. Nothing in the v1 schema needs Postgres-specific features.
- Alternative: force Docker everywhere; or hardcode SQLite and lose the prod story.
- Tradeoff: two DDL files to keep in sync, and SQLite gives up concurrent writers + native TIMESTAMPTZ. Acceptable because ingestion is single-process and dates are stored ISO8601.
- Interview q: "How would you deploy this?" → docker-compose.yml is in the repo; flip storage.mode to "docker" and nothing downstream changes, because no module imports a driver directly. That seam is the actual design decision — the specific databases are swappable details.

## 9. EDGAR ingestion: submissions API + fixed-interval rate limiter
- Problem: pull the right filing set (1 latest 10-K, last 4 10-Qs, recent earnings 8-Ks) per ticker without hitting SEC's fair-access limits.
- Choice: `data.sec.gov/submissions/CIK##########.json` gives a compact parallel-array list of every recent filing (form, date, accession, primaryDocument, items) in one request; filter/sort/slice in Python. A `RateLimiter` (fixed 1/max_rps interval, config-driven) wraps every outbound request; `documents.doc_id = accession` makes re-running the ingest idempotent (`SELECT` before `INSERT`, skip if present) with no separate flow runner needed.
- Alternative: full-text search API (`efts.sec.gov`) — better for keyword discovery, worse for "give me the N most recent filings of type X," which is what v1 needs.
- Interview q: "How do you pick which 8-Ks matter?" → most 8-Ks are non-events for RAG purposes (exec changes, unrelated 8-K items); filtering to Item 2.02 ("Results of Operations and Financial Condition") isolates the earnings-related ones, capped at `n_8k` (config) most recent.

## 10. 8-K primary document is not the earnings release — read the exhibit
- Problem: an 8-K's `primaryDocument` (from the submissions API) is the Inline-XBRL cover form — mostly machine-readable XBRL tag scaffolding, almost no narrative text. The actual earnings press release CLAUDE.md calls for (the free substitute for a paid transcript) is filed as a separate exhibit.
- Choice: for 8-Ks, fetch the filing's own `{accession}-index.html` and read its **Type** column (EDGAR-provided document metadata, e.g. `EX-99.1`) to find the earnings-release exhibit, and download that instead of `primaryDocument`. Verified against a real JPM 8-K: primary doc was 46KB of XBRL facts; the EX-99.1 exhibit was the actual "JPMORGAN CHASE & CO. EARNINGS RELEASE" narrative.
- Alternative: guess the exhibit by filename pattern (e.g. contains "ex99"). Rejected — filer/law-firm naming conventions vary; the Type column is authoritative and no more expensive (one extra rate-limited request per 8-K).
- Interview q: "How did you find that bug?" → didn't assume the API response was semantically what its field name implied; read the actual downloaded content before trusting the pipeline, which is what caught it (first ingestion run silently stored XBRL noise as the "filing" text).

## 11. Section parsing: line-anchored Item-header regex + TOC-vs-real span heuristic + Part scoping
- Problem: 10-K/10-Q HTML has no structural section tags — regex on "Item N" headers is the only cheap signal, but (a) filings open with a table of contents that repeats every heading, and (b) 10-Qs reuse item numbers across Part I and Part II with unrelated meanings (Part I Item 2 = MD&A; Part II Item 2 = "Unregistered Sales of Equity Securities").
- Choice: match `^item\s+<id>` at line start (real headers are their own block-level line after HTML stripping; TOC entries are too, so this alone doesn't disambiguate). For each wanted item id, keep the occurrence with the largest gap to the *next* Item heading of any kind — real sections run for pages, TOC entries are immediately followed by the next TOC line. For 10-Qs additionally track Part I/II boundaries and require each wanted item to fall in its correct Part, since item-id alone is ambiguous there.
- Verified against real filings: NVDA (4/4 10-Qs) and MSFT (3/3 10-Qs) parse cleanly with sane section sizes. **JPM's 10-Qs are the counter-example**: JPM never restates the "Item 1." header before the real Financial Statements content — only the TOC contains that exact text — so the span heuristic has no real occurrence to prefer and the section is under-sized (~2K chars of the true ~600K+). MD&A and Risk Factors parse correctly for JPM (those headers *are* restated). This is the "chunk-boundary case" carried into Phase 7's failure_cases.md rather than special-cased here.
- Alternative: parse the raw HTML DOM for bold/heading tags instead of text regex. More robust to this exact failure, but filer-specific formatting variance (font tags vs. CSS classes vs. inline styles across different 10-year-old EDGAR HTML dialects) trades one narrow failure mode for a different, harder-to-predict one. Deferred — not worth it for a 3-ticker v1; revisit if eval numbers show this actually costs recall.
- Interview q: "Why not just always take the last occurrence of each header?" → tried it conceptually; breaks the opposite way when a section is legitimately referenced late in the document (e.g., "Item 7A" cross-referenced from deep in "Item 9"). The span heuristic (biggest gap to the next heading) is a better proxy for "this is real content" than positional recency.

## 12. Chunk text lives in SQL only; Qdrant payload is metadata
- Problem: three stores now hold the same chunks (SQL rows, Qdrant points, BM25 corpus). Whoever holds the text is the one that must never be stale.
- Choice: `chunks.text` in the relational store is the single source of truth. Qdrant payload carries metadata only (ticker/company/doc_type/filing_date/filing_ts/fiscal_period/section/source_url/chunk_id/doc_id/chunk_index/n_tokens); the BM25 pickle carries tokens + metadata. Both retrievers return `chunk_id`s and hydrate text with one `WHERE chunk_id IN (...)` (`src/indexing/store.load_texts`).
- Alternative: duplicate the text into the Qdrant payload — one fewer round trip per query, self-contained vector store.
- Tradeoff: we pay a SQL fetch per search (single indexed PK lookup, negligible at any scale we'd hit) and gain the guarantee that changing chunking params can't leave a Qdrant payload disagreeing with the row a citation renders from. Payload also stays small enough to keep hot.
- Interview q: "Why not just store text in the vector DB?" → because then the same string exists in three places with no transaction spanning them, and the copy the *answer* quotes could differ from the copy the *citation* links to. Text in one store, keys everywhere else.

## 13. Deterministic point ids (uuid5) make re-indexing idempotent
- Problem: Qdrant ids must be int or UUID, but our join key is a readable string (`{accession}::{section}::{index}`); a random id per upsert silently duplicates every chunk on re-run.
- Choice: `point_id = uuid5(fixed_namespace, chunk_id)` — same chunk_id always maps to the same point, so upsert overwrites. The SQL write is `ON CONFLICT (chunk_id) DO UPDATE`, same property. Re-chunking a document explicitly deletes its old chunks in both stores first (`--rebuild`), because new params emit *different* chunk_ids that would otherwise coexist with the old ones.
- Alternative: hash to an int id (collision risk), or track an id counter (state to keep in sync).
- Interview q: "How do you re-index safely?" → idempotency is a property of the id function, not of the pipeline runner. Both smoke assertions double-upsert and assert the row/point counts didn't move.

## 14. BM25 persists a tokenized corpus, not a pickled BM25Okapi
- Problem: the sparse index needs to survive process restarts without recomputing from the DB every query.
- Choice: pickle plain lists — `chunk_ids`, token lists, metadata dicts — and rebuild `BM25Okapi` at load (sub-second at this corpus size). Tokenizer: lowercase, keep in-token `.`/`-` so `10-k`, `q3`, `1.5`, `u.s.` stay single terms, small hand-written stopword list, **no stemming**.
- Alternative: pickle the fitted BM25Okapi object (faster load, breaks on library upgrade — pickles of third-party classes are version-coupled); or use Postgres full-text search (real IDF + no separate artifact, but ties sparse retrieval to the Postgres path and gives up control of the tokenizer).
- Tradeoff on stemming: "impairment"/"impaired" stay distinct terms. Accepted deliberately — BM25 is in this system precisely for exact matches (tickers, "Blackwell", "CET1"), and the dense retriever already handles morphology. NLTK's default stopword list is also rejected: it strips "no"/"not", which invert meaning in risk-factor language ("no assurance").
- Interview q: "Why keep BM25 when embeddings are better?" → they aren't, on rare tokens. bge-small has never seen "GB200"; it lands somewhere generic in embedding space, while IDF weighting makes a rare token the strongest possible signal. Hybrid exists because the two fail on disjoint query types.

## 15. Filters pushed into the store, on both retrieval paths
- Problem: CLAUDE.md principle #4 (hard filters first, similarity second) is only true if the filter runs *inside* the search, not on its results. Post-filtering k results returns fewer than k — and sometimes zero — whenever the filter is selective.
- Choice: dense side uses a Qdrant `Filter` with explicit payload indexes on ticker/doc_type/section/fiscal_period/doc_id/chunk_id/filing_ts, so filtering is pushed into the HNSW traversal. Sparse side applies the same predicates to the score array *before* the top-k cut. Dates are stored twice — `filing_date` ISO string for display, `filing_ts` epoch integer for range filters — because integer `Range` behaves identically across Qdrant versions and the embedded local-mode client, while datetime-range support varies.
- Alternative: retrieve wide (k=200) and filter in Python. Works at 10k chunks, degrades exactly when the corpus grows.
- Interview q: "What breaks if you post-filter?" → recall silently, not loudly. Asking for 30 NVDA chunks and getting 4 looks like a sparse corpus, not a bug; that's why the Phase 2 smoke test asserts a filter both *keeps* the right hit and *excludes* the wrong one — an "everything returned matches the filter" assertion passes vacuously on zero results.

## 16. bge is asymmetric: separate passage and query encode paths
- Problem: bge-* models are trained with an instruction prefix on the query side only. Embedding a query bare costs real recall, and nothing errors — scores just quietly get worse.
- Choice: two functions in `src/common/embeddings.py` (`embed_passages`, `embed_query`), the prefix living in config and applied in exactly one place, rather than one function with a flag a caller can forget. Vectors are L2-normalized at encode time so Qdrant COSINE and raw dot product agree and downstream cosine math (dedup, clustering in Phase 5) needs no renormalization.
- Interview q: "How would you catch that regression?" → you don't catch it by reading scores; you catch it with the Phase 7 retrieval eval, which is why eval is not optional. The smoke test asserts normalization, but only recall@5 would reveal a missing prefix.

## 17. bge-small truncates at 512 wordpieces — `target_tokens` is 480, not 750
- Problem: CLAUDE.md specifies 600–900 token chunks, and the chunker's first draft targeted 750. `BAAI/bge-small-en-v1.5` is a BERT encoder with `max_seq_length = 512`, and that budget *includes* `[CLS]`/`[SEP]` — so a passage gets 510 wordpieces. sentence-transformers truncates past that silently: no exception, no warning on the encode path, a returned vector of the correct shape and correct norm. The only symptom is worse recall.
- Measured on a 9-document sample (one of each doc_type per ticker), re-chunked both ways:

  | target_tokens | chunks | chunks > 510 wp | corpus tokens never encoded |
  |---|---|---|---|
  | 750 | 1,072 | 1,046 (97.6%) | 214,335 (**28.3%**) |
  | 480 | 1,805 | 0 (0.0%) | 0 (0.0%) |

- The sharp edge isn't the loss, it's the **asymmetry**. Chunk text lives in SQL (DECISIONS #12) and BM25 tokenizes the whole thing, so at 750 the tail of every chunk stays fully searchable by the sparse arm, fully present in the text a citation renders, and invisible to the dense arm. The vector would have stopped representing the chunk it is indexed under — and hybrid retrieval would have papered over it, because BM25 keeps finding the tail and the fused result looks fine.
- Choice: `target_tokens: 480`, `overlap_tokens: 80`. 480 + the largest realistic overlap tail still clears 510 with room for the wordpiece expansion that financial text causes (tickers, "$1.5 billion", "CET1" all fragment into several wordpieces, so a token target measured with the model's own tokenizer — which is why `count_tokens` uses `AutoTokenizer`, not whitespace — is the only count that means anything). Live corpus confirms it: max `n_tokens` across all 3,456 chunks is exactly 480, zero chunks over 512.
- Alternative: keep 750 and accept truncation (rejected — silent, and worst on the longest/densest chunks, which are the financial tables); or switch to a long-context embedding model like `bge-m3` / `nomic-embed-text` at 8192 tokens (rejected for v1 — 3–5× the encode cost on Apple Silicon and a bigger index, to fix a problem that a config value fixes).
- Cost accepted: 480 is below CLAUDE.md's 600–900 band, and the corpus is ~68% larger in chunk count (1,072 → 1,805 on the sample). Smaller chunks cut both ways — better retrieval precision, less context per chunk for the generator, so Phase 6 may need to pass more than `final_top_k: 6` chunks.
- **Phase 7 eval item**: measure Recall@5 / MRR at `target_tokens` 480 vs 750 on the same 40 questions. The prediction is that 750 loses on questions whose evidence sits in the back half of a chunk, and that the loss is concentrated in `Financial Statements` (longest paragraphs, most wordpiece fragmentation). If 750 does *not* lose measurably, that is the more interesting result — it would mean the leading 510 tokens carry the retrievable signal and chunk size is mostly a generation-context decision, not a retrieval one.
- Interview q: "How would you have caught this in production?" → not from scores, which look normal; not from errors, because there are none. Two ways: assert `max(n_tokens) < model.max_seq_length` as an indexing invariant (cheap, catches it at write time), or catch it at eval time as a recall regression with no other explanation. This is the second thing in this build that the tokenizer-vs-whitespace distinction has decided — the first being the chunker's own packing loop.

## 18. Phase 3: one Retriever with a mode switch, not four retrieval code paths
- Problem: Phase 7 has to compare dense-only vs hybrid vs hybrid+rerank, and Phase 8 toggles between them live. If each strategy is its own call path, the A/B silently compares filter semantics, connection reuse and candidate widths alongside the retrievers themselves.
- Choice: `hybrid.Retriever` owns the Qdrant client, DB connection and BM25 index (lazily, so `bm25` mode doesn't require Qdrant to be up) and exposes `search(query, mode=dense|bm25|hybrid|rerank)`. `hybrid` and `rerank` share the *same* `_candidates()` fused pool, so the reranker's contribution is measured in isolation rather than against a differently-built candidate set. `top_k` controls only the returned list; the internal widths (dense 30, sparse 30, RRF top-30, final 6) always come from config.
- A `Filters` dataclass (`src/common/models.py`) carries the same five predicates to two unrelated engines — a Qdrant payload `Filter` on the dense side, a Python predicate over the BM25 score array on the sparse side. One object, so an eval arm cannot accidentally filter differently from the arm it's being compared against.
- `hydrate=False` skips the SQL text fetch for the eval harness, which scores `chunk_id`s and never reads text. `rerank()` raises on un-hydrated input rather than scoring empty strings — a cross-encoder given `("query", "")` returns a plausible number, so this failure would show up as mediocre ranking, not as an error.
- Observed on the live corpus (`scripts/smoke_retrieval.py`): for `"Blackwell"`, BM25's top-1 chunk ranks **22nd** on the dense side, and 8 of the 30 fused candidates are ones dense never surfaced. That is DECISIONS #14's argument for keeping BM25, now with a number attached — carried into Phase 7 as the BM25-wins case.
- Interview q: "Why rerank only 30?" → the cross-encoder is O(candidates) forward passes with full query-passage attention; 3,456 chunks per query is not a latency budget, it's an outage. The funnel is cheap-and-wide → expensive-and-narrow, and 30 is where the fused pool's recall has flattened. Whether 30 is actually the right width is a Phase 7 measurement, not a belief.

## 19. XBRL companyfacts: six traps, and why period derivation is computed not read
- Problem: `data.sec.gov/api/xbrl/companyfacts/CIK##########.json` is free and structured, which makes it look like a clean data source. It isn't. Every defect below produces *plausible numbers*, not errors, and each was verified against the real NVDA/MSFT/JPM payloads before being coded around.
- **(a) One tag holds several period lengths.** NVDA's `Revenues` contains 167 three-month, 37 six-month, 34 nine-month and 42 twelve-month facts in the same array. Loading the tag naively files a nine-month cumulative next to a quarter and calls both "Q3 revenue". Duration is derived from `start`/`end` and classified first; nothing unclassified reaches the DB.
- **(b) `fy`/`fp` describe the FILING, not the fact.** NVDA's quarter ending 2010-05-02 appears four times, labelled (fy=2010,fp=Q2), (2010,FY), (2011,Q1) and (2011,FY) — because a fact is re-reported as a comparative in every later filing that shows it. So fiscal period is *computed* from the fact's own `end` date against the company's fiscal-year-end month. This is the single most important decision in the module: the field that looks like the answer is the one you must not use.
- **(c) Fiscal calendars aren't calendar years.** NVDA's FY2026 ended 2026-01-25, MSFT's FY2026 ends 2026-06-30, JPM's is calendar. FYE month is inferred from each company's own annual facts; `fiscal_period()` is `fy = year(end) if month(end) <= fye else year(end)+1`, `qtr = ((month(end) - fye - 1) % 12)//3 + 1`. Verified against all three filers' own labels. Using only the month keeps 52/53-week filers (NVDA's quarter ends drift by days each year) working.
- **(d) The same period is reported many times** — 103 of 121 NVDA revenue periods. Latest `filed` wins, so a restatement supersedes the original and the 10-Q supersedes the 8-K release that preceded it. Tradeoff: we show what the company stands behind *now*, not what it said then; point-in-time history would need a bitemporal table, which v1 doesn't have a question for.
- **(e) Tags are industry-specific, and chain order is not enough.** Every candidate tag is a real tag with real facts — they're just from different eras. ASC 606 moved most filers to `RevenueFromContractWithCustomerExcludingAssessedTax` in 2018; NVDA stayed on `Revenues`; JPM moved to `RevenuesNetOfInterestExpense` in 2014. **Taking the first chain entry with any coverage silently truncated NVDA revenue to FY2018-FY2020 and JPM to FY2008-FY2014** — both wrong, both plausible, neither an error. Fixed by scoring candidates on coverage (recent quarters, then total, then latest period) with the anchor taken from the data so the choice is reproducible. The chosen tag is returned and printed per load, because "which us-gaap concept is this series" is the thing you must be able to audit later.
- **(f) Q4 is usually never filed.** 10-Qs cover Q1-Q3; the 10-K reports the year. JPM files zero standalone Q4 revenue facts. Q4 is derived as FY − 9M (one subtraction between two numbers from the same filing) falling back to FY − (Q1+Q2+Q3), flagged `derived = TRUE`. Applied only to additive flow metrics: **EPS is deliberately excluded**, because diluted share count moves quarter to quarter, so annual EPS is not the sum of quarterly EPS and a subtracted Q4 would be confidently wrong.
- Schema: added `period_end`, `source_accn` and `derived` to `financials`. `source_doc_id` is a FK into `documents`, which holds only the ~5 filings per ticker Phase 1 ingested out of the ~70 accessions companyfacts cites — setting it blindly violates the constraint, so it is populated only when we hold that filing and `source_accn` carries true provenance on every row. Migration is an idempotent `ensure_schema()` rather than a re-init, since the database already holds 3,456 chunks.
- **Writes replace a whole (ticker, metric) series, not just upsert.** Upsert makes re-running idempotent but cannot *retire* a row the new run no longer produces. When the JPM revenue tag was corrected, upsert left both eras in the table: one continuous-looking series with an invisible definitional break at 2014. Companyfacts always yields complete history, so there's no incremental case to protect.
- Interview q: "How do you know these numbers are right?" → I check the arithmetic against the source, not the pipeline against itself. NVDA FY2026Q4 revenue is asserted to equal 215.938B − 147.811B, the two facts it's derived from, and the whole smoke test is written as claims about the filings rather than as "it ran".

## 20. Canned parameterized queries, gap-aware growth, and no text-to-SQL in v1
- Problem: the NUMERIC route needs "revenue last 4 quarters", "QoQ/YoY growth", "margin trend" without letting a model emit SQL.
- Choice: `src/structured/queries.py` holds every query, fully parameterized; `QUERIES` is a name → (callable, param spec, description) registry the router selects from, and `run()` raises on an unknown query name *or* an unknown param, so a hallucinating router fails loudly instead of silently doing nothing. Text-to-SQL deferred to v2 for two stated reasons: injection risk (a generated string reaching the DB is an attack surface no prompt closes), and eval complexity (a wrong-but-plausible query returns a number, not an error).
- **The gap trap, which is the real content of this module.** The series has holes — Q4 EPS is never derived, and a filer can stop reporting a metric. `ORDER BY fiscal_year DESC, fiscal_qtr DESC LIMIT 4` then returns four rows that *look* contiguous but skip the hole, and pairing row N with row N+1 compares FY2027Q1 to FY2026Q3 while labelling it "quarter over quarter". So growth is computed against the **named** period (`prev_quarter` / `year_ago_quarter`), and `GrowthPoint.pct_change` is None when that period is absent. The smoke test asserts exactly this case on NVDA EPS.
- Values are normalized to `float` at the row boundary: Postgres NUMERIC yields `Decimal` and SQLite REAL yields `float`, so unnormalized arithmetic raises TypeError on one backend and works on the other — a storage-seam bug that only appears in the mode you didn't test.
- `available_metrics()` exists so "JPM gross margin" becomes an explicit *not reported by this filer* rather than an empty result the generator might render as zero. Same reasoning as insufficient-evidence in the RAG path: absence must be stated, not inferred.
- Interview q: "Why not just let the LLM write SQL against a 4-table schema?" → because I can't eval it. With eight canned queries I can assert the router picked the right one and the number is right; with generated SQL I'd be grading a string whose failure mode is a plausible wrong answer. That's a v2 problem to take on once there's a judge good enough to catch it.

## 21. News sources: three feeds, three different failure modes
- Problem: get ticker news without a paid API and without scraping anything licensed. RSS is the only source that stays free *and* legal, but "RSS" is three different things here and each breaks differently. All verified live before being designed around.
- **Google News search RSS** — best coverage (100 items/ticker) and it carries the publisher name in `<source>`, which is what source-diversity ranking needs. But every `link` is an opaque `news.google.com/rss/articles/CBM...` redirect that resolves to a JavaScript interstitial, not the article: fetching it returns HTTP 200 with the final URL still on news.google.com. **The real publisher URL is not recoverable**, so these items are headline-only — no body text, ever. Accepted rather than worked around: the alternatives are scraping Google (against their terms and fragile) or a paid news API (out of scope).
- **Yahoo Finance ticker RSS** — direct publisher URLs whose bodies trafilatura extracts about 80% of the time (thestreet.com and similar block it). But the "ticker" feed isn't ticker-scoped: a third of the NVDA feed was generic market content ("Worried About RMDs in Retirement? 3 Key Moves..."). Hence the alias relevance filter, applied to the *headline* — an article that never names the company in its headline isn't ticker news for a weekly brief.
- **Company IR feeds** — authoritative, direct URLs, body extractable every time (7/7 on NVDA, 9/10 on MSFT). All three tickers now have one. The earlier claim that MSFT's was stale and JPM had none was a **sourcing failure, not a fact about the companies**: `news.microsoft.com/feed/` parses fine and returns HTTP 200, which is why it was accepted — but its newest item is 2025-05-07, so a feed that looks healthy contributes nothing in a 7-day window. `news.microsoft.com/source/feed/` is the live one. JPM's newsroom path 404s, but the IR host carries the real feed at `jpmorganchaseco.gcs-web.com/rss/news-releases.xml`. **Lesson: validate a feed on the date of its newest item, not on HTTP 200 or on whether it parses.**
- JPM's IR feed is genuine but low-volume — 10 releases spanning 9 weeks, ~1.1/week, newest 24 days old — so it contributed **zero** items to the 7-day window on the day this was measured. That is correct behaviour, not a broken feed: it carries earnings releases, so it fires in the weeks that matter and is silent otherwise. Worth knowing before reading a quiet week as a bug.
- Consequence that shaped the pipeline: **37 of 209 non-duplicate articles have body text (17.7%), up from 26 of 199 (13.1%)** after fixing the two IR feeds and the survivor rule below. Google still supplies 176 of 216 collected items and 0 of the bodies. So the brief is still built to work from headlines — the fix improved the floor, it did not change the design premise, and anything needing full text degrades rather than fails.
- **Survivor rule: a resolvable URL beats an earlier Google redirect.** Near-dup survivorship was earliest-first, which quietly cost body text: when the same wire story arrives from both Google and Yahoo, the Google copy is often timestamped earlier, wins, and `hydrate_text` then skips the extractable Yahoo copy as a duplicate. Google being first is an artifact of feed latency, not of who broke the story. `_promote()` hands survivorship to the resolvable copy and re-points any `duplicate_of` already aimed at the loser, so the table never grows a chain into a row that is itself flagged duplicate. Small effect (2 articles across 3 tickers) but it is the mechanical meaning of "Google is the fallback".
- Interview q: "Your feed config looked fine and was silently broken for a third of your corpus — how would you catch that in prod?" → freshness is a monitorable property: assert per-feed `max(published_at)` is inside the lookback window and alert when a feed goes quiet. A feed that 200s forever while going stale is the failure mode that survives every liveness check you'd naturally write.
- Interview q: "Why not just resolve the Google redirect?" → I tried it. It's a JS interstitial, so you'd need a headless browser per article — which is both a scraping posture I don't want and a latency budget I don't have. The honest design is to use Google for *event detection* (headlines + publisher names, which is exactly what clustering and diversity ranking consume) and the direct feeds for text.

## 22. Headline embeddings are dominated by the company name — normalize before clustering
- Problem: with the thresholds CLAUDE.md specifies (0.90 near-dup, 0.75 cluster), the first live run produced one **39-article NVDA "event"** containing four unrelated opinion pieces, and flagged "Here's My Nvidia Stock Price Forecast" as a near-duplicate of "Nvidia's $279 Billion Bet Changes Everything". Both wrong, neither an error.
- Cause, measured on 67 live NVDA headlines: every headline about one company shares the company name, the exchange tag `(NASDAQ:NVDA)` and Google's ` - Publisher` suffix. That shared text contributes a *constant* similarity floor to every pair. Raw mean pairwise cosine 0.714 with **690 pairs** over the 0.75 cut; with those three elements stripped, 0.588 and **51 pairs** — a 13× reduction in spurious merges.
- Choice: `normalize_headline()` strips company aliases, exchange tags and the publisher suffix before embedding. Only the *vectors* see it; the stored headline stays verbatim, because the brief has to show what was actually published and a rewritten headline would make the citation disagree with the record. Result: the 39-article cluster resolved into coherent themes (price-prediction pieces; AI-chip-competition pieces), and NVDA went from 19 to 51 events over the same window.
- Tradeoff: the thresholds in config stay at CLAUDE.md's values rather than being re-tuned. That's deliberate — fixing the *input* to the similarity function is more durable than fitting a threshold to one week of one ticker's news, and it means the threshold stays comparable across tickers with different name frequencies.
- Honest limitation: what comes out are **topic clusters, not event clusters.** These feeds are dominated by commentary rather than reporting, so "five outlets published Nvidia price predictions this week" clusters cleanly while a discrete event may appear once. Recorded as FC-4.
- Interview q: "Why not just lower the threshold?" → because the problem isn't the cut point, it's that the signal has a constant added to it. Lowering the threshold trades one kind of error for another and has to be re-tuned per ticker; removing the constant fixes the geometry once.

## 23. Brief ranking: source diversity dominates, volume is capped
- Problem: rank clusters by importance. The obvious signal, article count, is actively wrong on this corpus. The single largest JPM cluster in a live window was **18 articles from one source** — MarketBeat's automated 13F posts, "$JPM Shares Acquired by <fund> LLC" with the fund name swapped. Volume says that's the week's biggest story. It isn't news.
- Choice: `score = n_sources + 0.25 * min(n_articles, 3)`. The cap is the point. Uncapped, the bot spam scored 5.5 and still outranked a real story ("India lifts ban on JPMorgan unit", 2 sources) at 2.5. Capping volume's contribution at 0.75 keeps it strictly below the value of one additional source, which makes the guarantee real rather than aspirational: **n articles from one source can never outrank n+1 sources, for any n.**
- Rationale: getting ten different newsrooms to cover something is the actual evidence of importance; getting one publisher to post the same template twenty times is evidence of a script. Dedup already collapses literal syndication; diversity ranking handles what dedup can't, because those 18 posts are genuinely *different* stories — just worthless ones.
- Near-duplicates are stored flagged rather than dropped, so the suppressed count is auditable and renderable ("3 near-duplicate reposts suppressed") instead of being invisible.
- Interview q: "Isn't source count gameable?" → yes, by syndication networks, and that's the next thing I'd measure. v1 counts distinct publisher names; v2 would weight by an outlet-reputation prior and treat wire pickups (AP/Reuters re-posts) as one source. Whether diversity ranking actually beats count ranking on human-judged importance is a Phase 7 measurement, not something I'm asserting.

## 24. Summarization degrades instead of failing
- Problem: the brief spec calls for LLM-written summaries with bull/bear implications, but generation is Phase 6 and Ollama may simply not be running.
- Choice: a thin `src/generation/llm.py` (one `complete()`, two backends, `available()` as a real socket check rather than a config read) and a brief that falls back to a **deterministic extractive summary** built from the headlines, clearly labelled in the rendered output. The fallback states who reported what and when, and *never* invents a bull/bear read — an unsupported implication is exactly the hallucination the citation contract elsewhere in this build exists to prevent, and the smoke test asserts the words "bull"/"bear" don't appear in it.
- Alternative: hard-fail when no LLM is reachable. Rejected — a brief you can't produce is worse than a plainer brief that is honest about how it was made, and the demo has to run on a laptop without Ollama.
- Interview q: "What's the risk with LLM summaries here?" → the source articles are mostly headlines (see #21), so a model asked for a bull/bear read has very little evidence and a strong prior. That's a groundedness problem, which is why Phase 7's judge scores the brief's claims against the headlines it cites rather than against whether it reads well.

## 25. A headline is not evidence: labelling context and declining implications
- Problem: 176 of 216 collected articles are Google News redirects with unrecoverable bodies, so most clusters reach the summarizer as headlines alone. Two defects compounded. `_numbered_context` passed **only headlines and never the body text at all** — the trafilatura extraction that ingestion works for was silently discarded before the prompt, so a full-text article and a headline-only one were byte-identical to the model. And `EVENT_SUMMARY_SYSTEM` *demanded* "bull implication, bear implication, potential market impact" unconditionally, which is an instruction to invent when the evidence is a single line of text. The pre-fix brief duly claimed analysts "cite its dominance in the AI and gaming markets" and attributed results to "a diversified product portfolio" — while citing [1] and [2], so the invention looked sourced. Fabrication that carries a citation is worse than an empty answer, because the citation is the thing a reader uses to decide whether to trust it.
- Choice: (a) the context builder labels every article `FULL TEXT` or `HEADLINE ONLY` and includes a 1500-char body excerpt when one exists; (b) the prompt carries an evidence rule that overrides the output format, forbidding causes, attributions, figures and strategic readings not in the headline; (c) the four interpretive sections must be the exact sentence `NO_SUPPORT` when every article in the cluster is headline-only, so declining is a first-class output rather than a formatting failure.
- Alternative rejected: an LLM judge scoring groundedness. It has the same blind spot as the generator — both read a fluent headline-derived claim as plausible — and it cannot fail a build deterministically. Phase 7's judge is for answer quality, not for this invariant.
- **The gate is the actual deliverable** (`scripts/smoke_headline_only.py`). Its fixture is three headlines that say *what* happened and never *why*, so any cause, attribution or figure is fabricated by construction. Checks are regex properties over the output: invented figures (every digit must trace to a headline, an article date, or a citation index), attribution to groups no headline quotes, asserted causes, projection, citation resolvability, and presence of the decline sentence.
- **Writing the gate is where the real lesson was.** The first draft asserted the obvious phrases — "analysts say", "due to" — and caught almost nothing: against the *old* prompt it fired on exactly one check, the sentinel, which is circular since only the new prompt mandates that phrase. Reading the actual pre-fix output showed the model rarely attributes to a named group. It writes *"is seen as a strategic expansion"*, *"are expected to support"*, *"is likely to have a positive impact"* — agentless hedging that reads as analysis while asserting things no headline contains. Widening to that class took the negative control from 1 violation to 4-10 per trial. A gate you haven't watched fail is not a gate.
- Two refinements the runs forced: the checks exempt a match whose text appears in the headlines (repeating "analysts expect" from a headline is reporting, not invention), and exempt matches inside a sentence *about the evidence* — "details are not available due to the headline-only nature" is the model correctly disclaiming its limits, and punishing that would train exactly the wrong behaviour. The exemption is sentence-scoped so a real claim next to a disclaimer still fails.
- Verified in both directions: 4/4 trials clean on the headline-only fixture, and a full-text fixture still produces grounded implications citing $3.2B, 1,800 jobs and Blackwell from the body — the constraint is scoped to the evidence, not a blanket gag.
- Consequence worth stating: for an all-headline-only cluster the generated summary now degenerates to roughly a list of the headlines, which is close to what the extractive fallback already produces. That is the honest output for that input, but it means **the LLM earns its place on full-text clusters and barely any on headline-only ones** — an argument for spending effort on body coverage rather than on prompt tuning.
- Interview q: "Your model stopped hallucinating because you told it not to — how do you know it holds?" → I don't trust the instruction, I test the property. The gate runs the generated path N times (generation is stochastic) and asserts deterministic properties over the text, and I keep the pre-fix prompt runnable as a negative control so I can show the gate failing the old behaviour on demand.
